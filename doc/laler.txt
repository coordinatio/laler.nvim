INTRO                                                              *laler-intro*

laler (Language Learner) helps you improve language use while writing in
Neovim: select text, run a prompt through a CLI LLM (pi, Cursor agent,
OpenCode, OpenAI-compatible HTTP, or custom), review several corrected
variants with a delta-style diff and learning notes, then apply one with
<CR>.

==============================================================================
SETUP                                                              *laler-setup*

>lua
  require("laler").setup({
    adapter = "pi",           -- "cursor" | "opencode" | "openai" | custom table
    model = nil,              -- CLI --model; required HTTP id for openai
    thinking = nil,           -- optional; false disables reasoning
    base_url = nil,           -- openai HTTP root; adapter table wins
    api_key_env = nil,        -- openai key env; adapter table wins
    api_key_file = nil,       -- openai key file; adapter table wins
    language = "en",
    n_variants = 3,
    default_prompt = "correct",
    remember_last_prompt = true,
    picker = nil,             -- "fzf-lua" | "telescope" | "vim_ui" | nil=auto
    timeout_ms = 60000,
    mappings = {
      run = "<leader>ll",
      pick = "<leader>lL",
      buffer = "<leader>la",
      pick_buffer = "<leader>lA",
    },
    -- prompts = { ... },    -- map: add/override; list: replace
  })
<

No mappings are created unless `mappings` is set.

==============================================================================
COMMANDS                                                        *laler-commands*

:[range]Laler [prompt]                                              *:Laler*
    Correct the given line range (default: current line) with [prompt],
    or the default/last-used prompt if omitted.

:[range]LalerPick                                               *:LalerPick*
    Open a prompt picker, then correct the range.

:LalerCancel                                                  *:LalerCancel*
    Cancel the in-flight job and close the review float.

==============================================================================
MAPPINGS                                                        *laler-mappings*

When configured:
  Normal: `run` / `pick` are operators — e.g. `<leader>llip`, `<leader>llap`
  Visual: `run` / `pick` use the current selection (char/line; not block)
  Normal: `buffer` corrects the whole buffer (same as `:%Laler`)
  Normal: `pick_buffer` picks a prompt, then corrects the whole buffer
             (same as `:%LalerPick`)

==============================================================================
REVIEW UI                                                         *laler-review*

After the model responds, a float shows:
  • header: prompt, variant index, adapter
  • unified two-tier diff (line + word highlights)
  • notes explaining language changes
  • key hints

Keys~
  <CR>       apply current variant to the original range
  Tab / n / ]   next variant
  S-Tab / p / [ previous variant
  1-9        jump to variant N
  y          yank variant text
  r          retry same prompt
  q / <Esc>  close (Esc also cancels while loading)

ADAPTERS                                                        *laler-adapters*

Built-ins (tools disabled so agents do not edit files):

  pi         `pi -p --no-tools --no-session --no-context-files --no-skills`
             (`--no-extensions` when no `model`; pi needs extensions to resolve
             `provider/model` IDs)
  cursor     `agent` or `cursor-agent` with `-p --mode ask --output-format text
             --trust --sandbox enabled` (ask is read-only; workspace trust;
             not `--force`)
  opencode   `opencode run --format default --pure`; OPENCODE_PERMISSION
             deny-all (no `--permissions` flag on `run`)
  openai     `exec curl` via `sh -c` to `POST {base_url}/chat/completions`
             (default `https://api.openai.com/v1`; not appended if the path
             already ends with `/chat/completions`, including a following
             `?query`). Requires `curl` and `sh`. Stdin is the chat-completions
             JSON body (`messages[].content` is the composed prompt).
             Key: if `api_key_env` is set and that env var is non-empty, use
             it; if the env var is empty/unset, fall back to `api_key_file`
             when set. Else `api_key_file`. Else, when the URL host is
             `api.openai.com` (nil `base_url` or an explicit official URL),
             `OPENAI_API_KEY`. Else omit `Authorization`. Never on argv.
             Other hosts do not use `OPENAI_API_KEY`; set `api_key_env` /
             `api_key_file` or omit auth. `model` is required
             (HTTP id). Top-level `base_url` / `api_key_env` / `api_key_file`
             work like `model`; on an adapter table, the table fields win.

When `model` is set (top-level or `adapter.model`), CLI built-ins add
`--model {name}`. For cursor it is inserted before the positional prompt.
The openai adapter puts `model` in the JSON body instead and requires it.
If both top-level `model` and `adapter.model` are set, `adapter.model` wins.
The same rule applies to openai `base_url` / `api_key_env` / `api_key_file`.

When `thinking` is `false` (top-level or `adapter.thinking`), pi adds
`--thinking off` and opencode adds `--variant none` (best-effort: some models
may still emit reasoning). The openai adapter is non-streaming. On a DashScope
host (DNS label `dashscope` or `dashscope-…`, e.g. `dashscope-intl.aliyuncs.com`)
or Alibaba MaaS (`maas.aliyuncs.com` / `*.maas.aliyuncs.com`), omit and `false`
both send `enable_thinking: false`; `thinking = true` is an error. On other
OpenAI-compatible hosts and on `api.openai.com`, the field is omitted
(`thinking = false` is a no-op; that field would 400). Cursor has no
thinking flag; choose a non-thinking model instead. If both top-level
`thinking` and `adapter.thinking` are set, `adapter.thinking` wins.

Generic adapters (`cmd` / `args` tables) append `--thinking off` for
`thinking = false` (pi-style). Only the built-in opencode adapter uses
`--variant none`.

Examples~
>lua
  require("laler").setup({
    adapter = "pi",
    model = "alibaba-cloud/qwen3.8-flash",
    thinking = false,
  })

  require("laler").setup({
    adapter = "cursor",
    model = "gpt-5",
  })

  require("laler").setup({
    adapter = "opencode",
    model = "anthropic/claude-sonnet-4-5",
    thinking = false,
  })

  require("laler").setup({
    adapter = "openai",
    model = "qwen3.8-flash",
    base_url = "https://dashscope-intl.aliyuncs.com/compatible-mode/v1",
    api_key_env = "DASHSCOPE_API_KEY",
    thinking = false,
  })

  require("laler").setup({
    adapter = {
      name = "openai",
      model = "qwen3.8-flash",
      base_url = "https://dashscope-intl.aliyuncs.com/compatible-mode/v1",
      api_key_env = "DASHSCOPE_API_KEY",
      api_key_file = "~/.config/laler/dashscope.key",
    },
    thinking = false,
  })

  require("laler").setup({
    adapter = {
      name = "pi",
      model = "alibaba-cloud/qwen3.8-flash",
      thinking = false,
    },
  })
<

Custom adapter table~
>lua
  require("laler").setup({
    adapter = {
      name = "my-cli",
      cmd = "my-llm",
      args = { "--print" },
      model = "my-model",       -- optional; appends --model
      thinking = false,         -- optional; --thinking off (not opencode --variant none)
    },
  })
<
Generic adapters append `--model` / `--thinking` to `args`; do not duplicate
those flags in `args` when also using `model` / `thinking` options.

With `build()`, `model` and `thinking` are ignored; emit argv flags in `build()`.
<

Or register at runtime:
>lua
  require("laler.llm").register("mine", client)
<

PROMPTS                                                          *laler-prompts*

Built-in ids: `correct`, `formal`, `casual`, `concise`.

Templates may use placeholders: `{{text}}`, `{{language}}`, `{{filetype}}`,
`{{n_variants}}`, `{{variant_noun}}`, `{{text_open}}`, `{{text_close}}`,
`{{variant_list}}`.
`{{text}}` is the passage wrapped in unique delimiters; `{{text_open}}` /
`{{text_close}}` are those delimiter strings; `{{n_variants}}` /
`{{variant_noun}}` are the requested count and "variant"/"variants";
`{{variant_list}}` is a numbered label list for that prompt
(`conservative` / `native` / `alternative` on `correct`; `{id}-1` … `{id}-n`
otherwise). The composer prepends a JSON-only output contract (language,
count, delimiters). Task templates only need the unique instruction plus
`{{text}}`. When you set `template` (new prompt or template override), it
must contain `{{text}}`. Overlays that omit `template` keep the builtin.
When set, `label` and `description` must be strings.

`prompts` as a map adds or overrides builtins and keeps the rest of the
catalog (older versions treated a map as a full replacement; use a list
for that). Overlaying a builtin merges fields: omitted `template` /
`label` / `description` stay. New map ids still need a `template`. If you
set `id`, it must equal the map key. `prompts` as a list still replaces
the catalog. Optional per-prompt `n_variants` (1–9) overrides the global
count. `default_prompt` selects the id for `:Laler` / `run` until a
successful run remembers another prompt (`remember_last_prompt`).

Add (map; builtins kept)~
>lua
  require("laler").setup({
    default_prompt = "conservative",
    prompts = {
      conservative = {
        label = "Conservative",
        n_variants = 1,
        template = [[Conservative correction: minimal edits, same meaning.

{{text}}]],
      },
    },
  })
<

Override a builtin (map; omitted fields stay)~
>lua
  require("laler").setup({
    prompts = {
      correct = { n_variants = 1 },
      concise = {
        template = [[Make the passage shorter. Keep technical terms.

{{text}}]],
      },
    },
  })
<

Replace the catalog (list)~
>lua
  require("laler").setup({
    default_prompt = "plain",
    prompts = {
      { id = "plain", template = [[Fix grammar only.

{{text}}]] },
    },
  })
<

Expected model JSON~
>json
  {
    "variants": [
      {
        "label": "native",
        "text": "...",
        "notes": ["why this change helps"]
      }
    ]
  }
<

==============================================================================
ARCHITECTURE                                                *laler-architecture*

SOLID-oriented Lua modules: `session` orchestrates ports wired in `setup()`.
Ports are documented in `lua/laler/contracts.lua`. Implementations live under
`llm/`, `picker/`, `diff/`, `view/`, `job/`, `parse/`, `prompt/`.
