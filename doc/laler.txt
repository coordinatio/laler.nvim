INTRO                                                              *laler-intro*

laler (Language Learner) helps you improve language use while writing in
Neovim: select text, run a prompt through a CLI LLM (pi, Cursor agent,
OpenCode, or custom), review several corrected variants with a delta-style
diff and learning notes, then apply one with <CR>.

==============================================================================
SETUP                                                              *laler-setup*

>lua
  require("laler").setup({
    adapter = "pi",           -- "cursor" | "opencode" | custom table
    model = nil,              -- optional CLI --model (all built-ins)
    thinking = nil,           -- optional; false disables reasoning
    language = "en",
    n_variants = 3,
    default_prompt = "correct",
    remember_last_prompt = true,
    picker = nil,             -- "fzf-lua" | "telescope" | "vim_ui" | nil=auto
    timeout_ms = 60000,
    mappings = {
      run = "<leader>ll",
      pick = "<leader>lL",
      buffer = "<leader>la",
      pick_buffer = "<leader>lA",
    },
    -- prompts = { ... },    -- override built-in prompt list
  })
<

No mappings are created unless `mappings` is set.

==============================================================================
COMMANDS                                                        *laler-commands*

:[range]Laler [prompt]                                              *:Laler*
    Correct the given line range (default: current line) with [prompt],
    or the default/last-used prompt if omitted.

:[range]LalerPick                                               *:LalerPick*
    Open a prompt picker, then correct the range.

:LalerCancel                                                  *:LalerCancel*
    Cancel the in-flight job and close the review float.

==============================================================================
MAPPINGS                                                        *laler-mappings*

When configured:
  Normal: `run` / `pick` are operators — e.g. `<leader>llip`, `<leader>llap`
  Visual: `run` / `pick` use the current selection (char/line; not block)
  Normal: `buffer` corrects the whole buffer (same as `:%Laler`)
  Normal: `pick_buffer` picks a prompt, then corrects the whole buffer
             (same as `:%LalerPick`)

==============================================================================
REVIEW UI                                                         *laler-review*

After the model responds, a float shows:
  • header: prompt, variant index, adapter
  • unified two-tier diff (line + word highlights)
  • notes explaining language changes
  • key hints

Keys~
  <CR>       apply current variant to the original range
  Tab / n / ]   next variant
  S-Tab / p / [ previous variant
  1-9        jump to variant N
  y          yank variant text
  r          retry same prompt
  q / <Esc>  close (Esc also cancels while loading)

ADAPTERS                                                        *laler-adapters*

Built-ins (tools disabled so agents do not edit files):

  pi         `pi -p --no-tools --no-session --no-context-files --no-skills`
             (`--no-extensions` when no `model`; pi needs extensions to resolve
             `provider/model` IDs)
  cursor     `agent` or `cursor-agent` with `-p --mode ask --output-format text
             --trust --sandbox enabled` (ask is read-only; workspace trust;
             not `--force`)
  opencode   `opencode run --format default --pure`; OPENCODE_PERMISSION
             deny-all (no `--permissions` flag on `run`)

When `model` is set (top-level or `adapter.model`), built-ins add
`--model {name}`. For cursor it is inserted before the positional prompt.
If both top-level `model` and `adapter.model` are set, `adapter.model` wins.

When `thinking` is `false` (top-level or `adapter.thinking`), pi adds
`--thinking off` and opencode adds `--variant none` (best-effort: some models
may still emit reasoning). Cursor has no thinking flag; choose a non-thinking
model instead. If both top-level `thinking` and `adapter.thinking` are set,
`adapter.thinking` wins.

Generic adapters (`cmd` / `args` tables) append `--thinking off` for
`thinking = false` (pi-style). Only the built-in opencode adapter uses
`--variant none`.

Examples~
>lua
  require("laler").setup({
    adapter = "pi",
    model = "alibaba-cloud/qwen3.8-flash",
    thinking = false,
  })

  require("laler").setup({
    adapter = "cursor",
    model = "gpt-5",
  })

  require("laler").setup({
    adapter = "opencode",
    model = "anthropic/claude-sonnet-4-5",
    thinking = false,
  })

  require("laler").setup({
    adapter = {
      name = "pi",
      model = "alibaba-cloud/qwen3.8-flash",
      thinking = false,
    },
  })
<

Custom adapter table~
>lua
  require("laler").setup({
    adapter = {
      name = "my-cli",
      cmd = "my-llm",
      args = { "--print" },
      model = "my-model",       -- optional; appends --model
      thinking = false,         -- optional; --thinking off (not opencode --variant none)
    },
  })
<
Generic adapters append `--model` / `--thinking` to `args`; do not duplicate
those flags in `args` when also using `model` / `thinking` options.

With `build()`, `model` and `thinking` are ignored; emit argv flags in `build()`.
<

Or register at runtime:
>lua
  require("laler.llm").register("mine", client)
<

PROMPTS                                                          *laler-prompts*

Built-in ids: `correct`, `formal`, `casual`, `concise`.

Templates may use placeholders: `{{text}}`, `{{language}}`, `{{filetype}}`,
`{{n_variants}}`, `{{text_open}}`, `{{text_close}}`, `{{variant_list}}`.
`{{text}}` is the passage wrapped in unique delimiters; `{{text_open}}` /
`{{text_close}}` are those delimiter strings; `{{variant_list}}` is a numbered
list of requested variant labels. The composer prepends a JSON-only output
contract.

Expected model JSON~
>json
  {
    "variants": [
      {
        "label": "native",
        "text": "...",
        "notes": ["why this change helps"]
      }
    ]
  }
<

==============================================================================
ARCHITECTURE                                                *laler-architecture*

SOLID-oriented Lua modules: `session` orchestrates ports wired in `setup()`.
Ports are documented in `lua/laler/contracts.lua`. Implementations live under
`llm/`, `picker/`, `diff/`, `view/`, `job/`, `parse/`, `prompt/`.
